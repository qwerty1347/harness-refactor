# 작업-02 — 판정 결과 문자열 리터럴을 모듈 상수로 올린다

입력 output(작업-01 위) · 89→92줄 · 새 파일 없음

상수 이름은 계획에 지정이 없어 값과 같은 어휘를 PEP 8 모듈 상수 표기로 올린 `APPROVED` / `REJECTED` 로 정했다. 파일 밖 어휘를 새로 들이지 않는 쪽을 골랐다.

## 변경

| 위치 | 한 것 |
|---|---|
| 1줄 뒤(신설 3·4줄) | `APPROVED` / `REJECTED` 선언. 값은 원문 리터럴 그대로, 애노테이션·신규 import 없음 |
| 37·43·45·50·55·58줄 → 40·46·48·53·58·61줄 | `"rejected"` 6곳을 `REJECTED` 참조로 교체 |
| 38·41·48·53줄 → 41·44·51·56줄 | `"approved"` 4곳을 `APPROVED` 참조로 교체 |

## 확인

| 계획의 확인 항목 | 결과 |
|---|---|
| `"approved"` / `"rejected"` 리터럴이 상수 선언 2줄 외에 잔존하지 않는가 | **부분 통과** — 코드 리터럴은 3·4줄 두 곳뿐. 다만 작업-01이 쓴 32줄 독스트링 본문에 두 단어가 인용부호째 들어 있어 Grep 문자열 일치로는 잡힌다. 실행 경로가 아니라 손대지 않았다 |
| 상수 참조 `return` 이 정확히 10개이고 원문 승인/거부 배치와 1:1 대응하는가 | 통과 — 거부 6개(원문 37·43·45·50·55·58) / 승인 4개(원문 38·41·48·53), 순서·위치 그대로 대응 |
| 조건식·분기 구조가 작업 전후 문자 수준 동일한가 | 통과 — `if`/`else`/`for` 9개 조건줄과 들여쓰기 전부 대조 완료 |

## 계획 밖

| 위치 | 내용 |
|---|---|
| 32줄 | 작업-01의 독스트링이 판정 결과를 인용부호 붙은 원시 단어로 서술해, 상수화 이후에도 값이 문서에 이중으로 박혀 있다 |
| 28줄(원문 19줄 반환 타입) | 반환 타입 `str` 이 두 상수만 유효하다는 사실을 여전히 표현하지 못한다 (항목-03 잔여층, 계획에 남기기로 명시됨) |

# 작업-03 — `approve_order` 분기를 조기 반환 가드로 평탄화

입력 output(작업-02 위) · 92→84줄 · 새 파일 없음

계획 31~55줄 → 입력 34~58줄(작업-02가 상수 3줄을 앞에 넣어 3줄 밀림). 조건식 내용으로 찾아 진행했다.
`order.amount > 1000` 을 계획이 지시한 `<=` 반대 방향 비교로 뒤집었다. `not (... > ...)` 이 아니라 계획 문구 그대로를 골랐고, 그 결과 `amount` 가 `float("nan")` 일 때만 원문과 갈래가 갈린다(아래 확인 2행).

## 변경

| 위치 | 한 것 |
|---|---|
| 34·35·36·37줄 | 바깥 4개 분기를 조기 반환 가드로 역전 (`not user.is_premium` / `order.amount <= 1000` / `order.has_discount` / `user.region == "EU"`). 평가 순서 그대로 |
| 42·45·47·49·52·54·57줄 | `else:` 7개 제거, 뒤따르던 블록을 한 단계씩 바깥으로 이동 |
| 38~41·43~44·50~51·55~56줄 | `for` 순회·음수 가격 검사·통화 비교·`and` 결합 bulk 조건·관리자 분기를 원문 문자 그대로 옮김 |
| 33줄·59~61줄 | `try:` / `except Exception:` / 주석 / 마지막 `return` 골격 손대지 않음 |

## 확인

| 계획의 확인 항목 | 결과 |
|---|---|
| 함수 본문 `else` 0건 | 통과 — 파일 전체에 `else` 없음 |
| `return` 10개이며 각 반환값이 원문의 같은 조건 조합에 대응 | 통과 — 9개 갈래(프리미엄X+관리자O/X, 소액+bulk조건O/X, 할인, EU+EUR O/X, 비EU+음수가격O/X)와 `except` 1개를 진리표로 1:1 대조 |
| 조건식이 원문 9개의 부정·역방향 1:1 대응이며 병합·신설 없음 | **부분 통과** — 8개는 대응 확인. `order.amount <= 1000` 만 `not (order.amount > 1000)` 과 NaN 입력에서 갈린다(원문은 bulk 갈래, 결과물은 할인 갈래). 계획 문구를 따른 결과이며 판단이 필요하다 |
| 최대 들여쓰기 감소 · `def` 줄 원문 동일 | 통과 — 32칸 → 16칸, `def approve_order(order: Order, user: User) -> str:` 동일 |

| 위치 | 내용 |
|---|---|
| 50줄(결과물) | 비EU 경로에만 있는 음수 가격 검사가 나머지 반환 경로에 없다 (항목-09, 판단 필요로 명시됨) |
| 37줄(결과물) | 지역 판정이 `user.region` 이고 `main` 은 `order.region` 에 다른 값을 넣는다 (항목-06, 판단 필요로 명시됨) |
