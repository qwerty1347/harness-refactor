# harness-refactor

레거시 코드를 **구조만** 리팩토링하는 Claude Code 하네스.

파일 하나를 진단하고, 작업 계획을 세우고, 리팩토링한 코드를 만든 뒤 검토까지 한다.
**원본은 건드리지 않는다** — 결과물은 `_workspace/output/` 에 나오고 적용은 사람이 한다.

## 무엇을 하고 무엇을 안 하나

**코드를 옮기기만 한다.** 메서드·클래스로 추출하고, 파일을 나누고, 호출로 교체한다.
옮긴 코드는 원문과 문자 수준에서 같다 — 조건식·리터럴을 손대지 않고, 방어 코드나 타입 힌트를 더하지 않는다.

동작이 바뀌는 것은 **묻지 않고 뺀다.** 이유를 모르는 코드도 그대로 둔다.
레거시의 이상한 코드에는 대개 이유가 있고, 그 이유는 파일 안에 없다.

추출은 **두 곳 이상 반복되고, 여러 단계가 묶이고, 같은 개념일 때만** 한다.
한 줄을 감싸는 래퍼는 만들지 않는다 — 이름 읽고 정의로 점프하는 비용이 원문 읽는 비용보다 크다.

## 기계가 보증하는 두 가지

나머지는 모델 판단이지만, 이 둘은 세거나 대조해서 확인된다.

**근거 대조** — 프로젝트 설정 파일(`.editorconfig` 등)에 적힌 규정마다 대상 파일이 지키는지 본다.
도구 없이 판정 못 하는 항목은 `검사 불가` 로 남기고 **0 건으로 적지 않는다.**
돌리지 않은 것을 통과했다고 쓰는 것이 이 리포트에서 가장 나쁜 실패다.

설정 파일에 `preset: {이름}` 한 줄만 있다면 그 프리셋이 품은 규칙은 **파일에 없는 것**이다.
프로젝트가 선언한 규정으로 취급하지 않는다.

**위치 검산** — 지적한 위치를 `Grep` 으로 세어 인용과 맞춘다. 두 방향으로 본다.

```
{심볼}      → Grep 9곳
항목의 인용  →      6곳     ← 3곳이 설명되지 않았다
```

암산으로 세면 반드시 빠진다. 실제로 같은 파일에서 9곳 중 6곳만 잡힌 적이 다섯 번 연속 있었다.
빠진 위치는 그만큼 옮겨지지 않고 코드에 남는다.

## 구성

| | 이름 | 도구 | 하는 일 |
|---|---|---|---|
| 스킬 | `refactor` | — | 오케스트레이터. 대상 확정 · 스택 판정 · 근거 수집 · 에이전트 순차 실행 |
| 에이전트 | `legacy-analyzer` | `Read` `Grep` `Write` | 대상 파일 진단. 무엇이 문제이고 어디에 있는지 |
| 에이전트 | `refactoring-strategist` | `Read` `Write` | 발견 항목을 작업으로 묶고 안전순으로 줄 세움 |
| 에이전트 | `refactoring-engineer` | `Read` `Write` | 작업 하나씩 실행. 결과물을 `output/` 에 |
| 에이전트 | `modernization-reviewer` | `Read` `Grep` `Write` | 단계 사이가 어긋난 곳을 찾음 |

도구를 좁힌 것이 안전장치다. `Edit` 이 없으므로 기존 파일을 부분 수정할 수 없고,
`Glob` 이 없으므로 프로젝트를 탐색할 수 없다.
analyzer 의 `Grep` 은 **대조와 검산 전용**이며 `path` 에 대상 파일만 넘긴다.

## 실행

대상 프로젝트 디렉토리에서 실행한다.

```
/refactor {리팩토링 대상 파일}
```

인자 없이 부르면 전체를 스캔하지 않고 대상을 물어본다.
범위를 좁히려면 `T3까지`, 다시 만들려면 `새로` 를 붙인다.

**한 번 부르면 끝까지 간다. 중간에 묻지 않는다.**
멈추는 것은 대상 파일을 못 찾거나 작업 하나가 실패했을 때뿐이다.

> 에이전트 md 를 고치면 세션을 다시 열어야 반영된다. 실행 중인 세션은 옛 정의를 쓴다.

## 산출물

CWD 기준으로 생긴다. 대상 프로젝트에 남는 흔적은 이 폴더뿐이고, 기존 파일은 하나도 바뀌지 않는다.

```
_workspace/
├── 00_input.md                  스택 · 확정 하한 · 제외 문법 · 근거 목록
├── 01_legacy_analysis.md        진단 — 의존 목록 · 관심사 지도 · 발견 항목 · 근거 대조 · 검산
├── 02_refactoring_strategy.md   계획 — 작업 목록 · 다루지 않은 F-ID
├── 03_migration_plan.md         실행 기록 — 작업당 20줄
├── 04_review_report.md          검토 — 작업별 O/X · 적용 전 돌려볼 것
└── output/                      리팩토링 결과물 (원본 디렉토리 구조 그대로)
```

적용은 diff 를 보고 사람이 한다.

```
diff -r app/ _workspace/output/app/
```

`00_input.md` 가 스택 종속을 혼자 떠안는다. 확정 하한은 선언값만 믿지 않고 lock 파일로 교차 확인한다.

```markdown
- 확정 하한: {언어} {버전}
  ({선언 파일} 은 {선언값} 이나, lock 에 {더 높은 제약} 요구 패키지 존재)
```

설치된 패키지가 선언보다 높은 버전을 요구하면 **실제 하한이 올라간다.**
선언만 믿으면 쓸 수 있는 문법을 못 쓴다고 판단하게 된다.

에이전트들은 스택을 모른다. 버전별 문법 표도 프레임워크 관례도 들고 있지 않다.
언어를 추가할 때 손댈 곳은 스킬의 판정 표와 제외 목록뿐이다.

## 알려진 제약

| 제약 | |
|---|---|
| 코드를 실행하지 않는다 | 테스트도 정적 도구도 안 돌린다. 동작 확인은 사람 몫이다 |
| 호출자를 보지 않는다 | 분석은 대상 파일 안에서 끝난다. 시그니처·가시성이 바뀌는 작업은 범위 밖 |
| `docs/conventions/` 가 비어 있다 | 프로젝트가 선언한 구조 규칙이 없으면 기계로 대조할 것도 그만큼 줄어든다 |
| Python / FastAPI 는 설계만 | 실제 실행 미확인 |
